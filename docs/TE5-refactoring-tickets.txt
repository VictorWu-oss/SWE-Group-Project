Ticket R-01: Extract Discovery Logic from the Map Screen (SELECTED)

Location: packages/mobile-app/src/2d/CampusMapScreen.tsx

Problem:
The screen handles search filtering, distance calculations, sorting, and UI rendering in one component. This makes the component difficult to read and makes the discovery logic difficult to test.

Code Smell:
Large component, mixed responsibilities, and difficult-to-test logic.

Clean Code Concept:
Single Responsibility Principle and Extract Method.

Priority:
P1 - High

Proposed Refactoring:
Move search, distance, sorting, and formatting logic into a separate utility module such as packages/mobile-app/src/main/discovery.ts. Add unit tests for search matches, no results, distance ordering, and alphabetical ordering.

Old Code:

const orderedBathrooms = bathrooms
  .filter((bathroom) => `${bathroom.name} ${bathroom.building}`
    .toLowerCase().includes(search.trim().toLowerCase()))
  .map((bathroom) => ({
    bathroom,
    distanceKilometers: location && bathroom.latitude !== null
      ? distanceBetween(location, {
        latitude: bathroom.latitude,
        longitude: bathroom.longitude,
      })
      : null,
  }))
  .sort((first, second) => {
    const firstDistance = first.distanceKilometers ?? Number.POSITIVE_INFINITY;
    const secondDistance = second.distanceKilometers ?? Number.POSITIVE_INFINITY;
    return location
      ? firstDistance - secondDistance
      : first.bathroom.name.localeCompare(second.bathroom.name);
  });

New Code:

const orderedBathrooms = useMemo(
  () => filterAndSortBathrooms(
    bathrooms,
    search,
    location,

  ),

Why We Refactored It:
The original screen combined user-interface rendering with search and sorting rules. We moved the discovery calculations into discovery.ts so the screen is responsible mainly for state and rendering. The new implementation is easier to read, reuse, and test.

Reviewer Comments:

Testing/Verification:

Ticket R-02: Consolidate Bathroom Summary Database Queries (SELECTED)

Location: packages/express-backend/src/services/reviewService.js

Problem:
The list and detail operations contain overlapping database-query and mapping logic. The detail lookup previously loaded unnecessary records and searched through them in memory.

Code Smell:
Duplicate logic, inefficient implementation, and possible inconsistency between list and detail responses.

Clean Code Concept:
Don't Repeat Yourself (DRY) and Extract Method.

Priority:
P1 - High

Proposed Refactoring:
Create one reusable parameterized query function that supports full lists, search queries, and individual bathroom IDs. Reuse the same projection and row-mapping logic for both list and detail endpoints.

Old Code:

function getBathroomSummary(database, bathroomId, installationId) {
  const rows = getAllBathroomRows(database, installationId);
  const row = rows.find((bathroom) => bathroom.id === bathroomId);
  return row ? mapDirectoryBathroom(row) : null;
}

New Code:

function getBathroomSummary(database, bathroomId, installationId, date = new Date()) {
  const [row] = getBathroomRows(database, installationId, date, { bathroomId });
  return row ? mapDirectoryBathroom(row, date) : null;
}

function getBathroomRows(database, installationId, date, { bathroomId, search } = {}) {
  const filters = [];
  const parameters = [installationId, getLosAngelesDay(date)];

  if (typeof bathroomId === 'string') {
    filters.push('b.id = ?');
    parameters.push(bathroomId);
  }

  const whereClause = filters.length > 0 ? `WHERE ${filters.join(' AND ')}` : '';
  return database.prepare(`
    SELECT b.*, COUNT(r.id) AS review_count,
      AVG(r.cleanliness) AS average_cleanliness
    FROM bathrooms b
    LEFT JOIN reviews r ON r.bathroom_id = b.id
    ${whereClause}
    GROUP BY b.id
    ORDER BY b.name COLLATE NOCASE
  `).all(...parameters);
}

Why We Refactored It:
The old implementation used separate logic for list and detail operations. This could make the responses inconsistent and caused the detail operation to retrieve more data than necessary. The new shared query reduces duplication, performs a more focused lookup, and keeps the response mapping consistent.

Reviewer Comments:
The reviewer should confirm that list responses, search results, detail responses, unknown bathroom IDs, review counts, and average cleanliness values are unchanged.

Testing/Verification:
The backend tests verify list ordering, case-insensitive search, empty search results, detail lookup, unknown IDs, and review aggregates.


Ticket R-03: Separate Review Validation from Review Persistence (SELECTED)

Location: packages/express-backend/src/services/reviewService.js, especially submitReview

Problem:
The submitReview function validates request fields while also managing transactions, duplicate checks, database inserts, updates, and error handling.

Code Smell:
Long method and mixed responsibilities.

Clean Code Concept:
Single Responsibility Principle and Extract Method.

Priority:
P2 - Medium

Proposed Refactoring:
Extract review-input validation into a separate validateReviewInput function. Keep database transactions and persistence inside submitReview. This makes validation independently testable and makes the persistence logic easier to follow.

Old Code:

function submitReview(database, input, now = new Date()) {
  if (!input || typeof input !== 'object') {
    throw validationError('A review request body is required.');
  }
  if (!Number.isInteger(input.cleanliness)
      || input.cleanliness < 1 || input.cleanliness > 5) {
    throw validationError('Cleanliness must be a whole number from 1 to 5.');
  }

  database.exec('BEGIN IMMEDIATE');
  // Validation, duplicate checks, insert, update, and commit were mixed here.
}

New Code:

function submitReview(database, input, now = new Date()) {
  const { bathroomId, installationId, cleanliness, busyness } = validateReviewInput(input);
  const day = getLosAngelesDay(now);
  const timestamp = now.toISOString();

  database.exec('BEGIN IMMEDIATE');
  try {
    // The transaction now contains only lookup and persistence work.
    database.prepare(`
      INSERT INTO reviews
        (bathroom_id, installation_id, review_day, cleanliness, busyness, created_at)
      VALUES (?, ?, ?, ?, ?, ?)
    `).run(bathroomId, installationId, day, cleanliness, busyness, timestamp);
    database.exec('COMMIT');
  } catch (error) {
    database.exec('ROLLBACK');
    throw error;
  }
}

function validateReviewInput(input) {
  if (typeof input !== 'object' || input === null || Array.isArray(input)) {
    throw Object.assign(new Error('A review request body is required.'), { statusCode: 400 });
  }
  if (!Number.isInteger(input.cleanliness)
      || input.cleanliness < 1 || input.cleanliness > 5) {
    throw Object.assign(new Error(
      'Cleanliness must be a whole number from 1 to 5.'
    ), { statusCode: 400 });
  }
  return input;
}

Why We Refactored It:
The original function mixed input validation with database persistence and transaction management. We extracted validation into validateReviewInput so each function has one clear responsibility. The new version is easier to understand and allows validation to be tested independently.

Reviewer Comments:
The reviewer should confirm that invalid requests are rejected before a transaction begins and that valid reviews, duplicate reviews, and database rollback behavior still work correctly.

Testing/Verification:
The backend tests cover valid submissions, invalid cleanliness values, malformed requests, unknown bathrooms, duplicate submissions, Los Angeles calendar-day behavior, and persistence after a database restart.
